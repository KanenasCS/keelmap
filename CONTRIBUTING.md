# Contributing

Thanks for helping. KeelMap has one rule above all others: it reports what the
traffic proves, nothing more. Read [docs/precision-contract.md](docs/precision-contract.md)
before changing a decoder.

## Setup

```
python -m venv .venv && . .venv/bin/activate
pip install -e ".[dev]"
pytest
ruff check src tests tools
```

Install tshark (`apt install tshark`) to run the tests that compare against it.
They are skipped otherwise.

## Adding or changing a decoder

1. Document what it stores, what it deliberately does not store, and the counter for every skip, in `docs/decoders.md`.
2. Every value goes through `Attested.add`, `AttestedSet.add` or `Communication.record`. Never write fields directly.
3. Pick the evidence kind honestly. Something a device says about itself is `self_reported`, behaviour seen in traffic is `observed`. There is no inferred kind, on purpose.
4. Validate against an independent reference, such as tshark or a well-known protocol library, on public captures, and record the result in the validation log in `docs/decoders.md`. Explain every difference, do not tune until the numbers match.
5. Bump the decoder version when its output changes.

## Test data

- Never commit real captures. `.gitignore` blocks `*.pcap` and `*.pcapng` except in `tests/fixtures/public/`.
- Public fixtures need a redistributable licence and a `*.source.md` entry with source, licence, SHA-256 and reference values.
- Expected results are written from an independent tool or by hand from Wireshark, never generated by KeelMap.

## Chart changes

Captured strings must reach the page only through `textContent` or canvas labels.
Run `tools/make_hostile_map.py` and `tools/check_map_browser.js` after changing
anything in `src/keelmap/report/`.

## Writing style

Plain sentences in docs and messages. Name things by what users see, not how the code is built.
